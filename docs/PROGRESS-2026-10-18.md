# RadeonNI Leopard driver progress

Updated: 2026-10-18, approximately 17:00 MDT.

### Follow-up: text selection, approximately 17:20 MDT

Reproduced white rectangular holes in System Profiler's selection highlight
and stray screen squares with the software cursor. Moving the window cleared
the corruption. Enabled the existing DCE hardware cursor (`HWCursor = true`)
in the installed personality, rebuilt caches and rebooted. The same selection
drag then produced three clean captures; cursor control register `0x6998`
reported `0x04000201`, including while the pointer was over selectable text.

Kernel and GLD binaries were unchanged for this fix. Accelerated Leopard
installs now enable the hardware cursor by default. Evidence is under
`private/selection-compositing/`; the original personality is backed up on
the Mac as `display-power-review/Info-before-hwcursor.plist`.

This resolves the reproduced selection corruption on the tested hardware
cursor path. The software-cursor fallback still needs proper synchronization
with asynchronous compositor writes; this does not establish a general fix
for all surface corruption or the Portal hang.

This report describes the work recorded in this checkout and the current
Power Mac test session. It separates code changes from observed results.
The existing RadeonNI hardware library and Mesa r600 driver are the foundation;
this work adapts, corrects and extends that implementation rather than creating
a complete GPU driver from scratch.

## 1. Leopard OpenGL integration

### Changes

- Distinguished Leopard 10.5.8's 757-entry dispatch layout from the
  759-entry layout recorded for 10.5.9; retained the separate Tiger layout.
- Corrected dispatch-header parsing so comments do not hide declarations.
- Added or corrected the Leopard context/dispatch handling needed to reach
  Mesa through Apple's OpenGL framework.
- Corrected default-framebuffer viewport, scissor and read-coordinate
  translation. Screen offsets must not be applied to application FBOs.
- Adjusted viewport/scissor state when switching between the default
  framebuffer and an FBO, and corrected the corresponding queried values.
- Handled Leopard's zero-valued byte-stride reset during pixel uploads.
- Kept a Leopard compatibility exposure of OpenGL 2.1 / GLSL 1.20 and removed
  the ARB framebuffer-object advertisement on that path.

### What that establishes

These changes address ABI and coordinate correctness, including missing or
misrouted entry points and rendering into the wrong part of a drawable.
They do not implement OpenGL 4.6. Compatibility version strings are a policy
choice, not evidence that every advertised feature passes conformance tests.
Chromium and the entire game library have not received complete launch and
rendering qualification.

Main files: `gld/rdn_engine.h`, `gld/gen_dispatch.py`,
`gld/RadeonNIGLDriver.c`, `gld/rdn_mesa.c`.

## 3. GPU submission and memory lifetime

### Changes

- Corrected fence-publication handling in the submission path.
- Added client-close cleanup that stops future compositor references to the
  client's stores and waits for submitted GPU work before releasing memory.
- On cleanup timeout, retains GPU-visible memory instead of freeing memory
  that the GPU may still access.

### Limits

Retaining allocations after a hang avoids a dangerous reuse path, but can
retain memory until reboot. It is not GPU recovery or a replacement for
per-buffer ownership, access validation and reference-counted retirement.
Neither the fence correction nor the client-close change resolved Portal's
gameplay hang.

Main files: `kext/RadeonNI/RadeonNIAccel.cpp`, `hw/rdn_user.h`,
`mesa/winsys/rdn_winsys.c`, `mesa/patches/0008-glthread-done-callback.patch`.

## 4. Portal hang investigation

### Diagnostic work actually added

- Bounded, opt-in command submission capture: command words, buffer IDs,
  addresses, sizes, access flags, prior fences and submission results.
- Sixteen capture slots; submissions with unfinished fences are protected
  from normal slot rotation.
- Optional GPU command-processor progress markers after draw packets.
- A native `hangwatch` helper that reads progress without mapping the entire
  aperture or forcing an HDP flush.
- Offline IB decoding and logical vertex-attribute range checks.
- Correct PowerPC byte order for Mesa's diagnostic trace counter.
- More reliable per-patch checking in the Leopard Mesa build process.

### Findings

Two captured failures stalled at submissions `0x78a0` and `0x602f`. The latter
contained 282 draws and reached marker 262. This is command-processor progress,
not proof that draw 263 caused the hang or that earlier rendering completed.

Saved CPU submissions matched the GPU IB bytes. Supported logical attribute
checks found 871 and 1,176 accesses within their descriptors in the two runs.
That does not validate texture addressing, resource lifetime, speculative
fetches, or earlier corruption. Hidden VRAM texture contents were not captured.

The glthread profile did not eliminate the hang. It is not recorded as a fix.
There is no proven root cause, reduced reproducer, or working GPU-reset recovery.

Evidence: `private/capture-hang-20261018/`,
`private/marker-hang-20261018/`, `tools/diagnostics/rdn_ib.py`,
`tools/guest/hangwatch.c`.

## 6. Display power and the boot regression

### Regression, recovery and correction

An earlier candidate registered power management in `start()`, before
IOFramebuffer initialized its shared machinery. It caused the rainbow-bars /
1280x800 boot failure. The saved panic showed an uninitialized event-gate
access in `IOEventSource::closeGate` through IOGraphicsFamily.

The working kernel was restored using the X1900 recovery boot, with cache
rebuilding and binary verification. The user confirmed recovery.

Power registration was then moved to `enableController()`, following Apple's
IOGraphics-193.2 lifecycle, with one-time registration and error checking.
The corrected candidate passed a native build and loadability check and was
installed and successfully rebooted during the latest session.

### Further power fixes

- Added explicit framebuffer power states and interpreted connection-power
  flags using `kFBDisplayUsablePowerState`.
- Separated monitor and framebuffer power requests. Scanout is requested on
  only when both permit it, regardless of wake-request order.
- Avoided duplicate on/off notifications for transitions between two
  non-usable framebuffer states.
- Tracked the stopped CRTC even if disabling the transmitter reports an
  error, allowing a later wake to reprogram the output.
- Serialized the post-wake hotplug debounce reset.

The power test executes the production request method with both wake orders,
redundant requests, wake failure/retry and transmitter-disable failure.
It passes. This is state-machine coverage, not physical sleep qualification.

The live test logged connection-power transitions, but did not establish a
complete display-off/wake cycle before work switched to this report. The
temporary one-minute display timer and disabled system-idle timer were restored
to the original settings. **Display sleep/wake is not yet qualified.**

## 7. Full system sleep: unfinished

The driver still advertises `SystemSleepSupported = No` and retains
`kIOPMPreventSystemSleep`. A successful reboot or display-power transition
does not establish suspend/resume support.

A new local `rdn_gart_resume()` path reprograms translation without replacing
live page-table entries with the dummy page. Its host test passes, including
preservation of mappings across disable/resume. This change is **not in the
currently installed kernel** and is not wired into a system-sleep lifecycle.

Still required:

1. Block submissions and CPU access appropriately, then drain GPU work with
   bounded failure handling before suspend.
2. Preserve allocated VRAM, including memory outside the 256 MB CPU aperture.
3. Restore PCI/ASIC/MC, clocks, GART, command processor and fence state in order.
4. Restore or invalidate GPU context state coherently with Mesa and live clients.
5. Restore displays, cursor, LUTs and changed monitor configuration.
6. Handle failed suspend/resume without freeing live GPU resources or falsely
   acknowledging a usable device.
7. Pass physical sleep/wake cycles with live applications and tracing disabled.

The GART helper addresses one prerequisite, not the complete feature.

## Legacy 2D and surface readbacks follow-up

- `RadeonNIGA` now submits 32-bit screen fills/copies to the GPU by default.
  The `/tmp/rdnga.gpu` opt-in is no longer required. Other pixel depths retain
  their existing CPU implementation.
- Submission errors propagate through fill/copy/region callbacks and latch the
  connection in an error state. No CPU retry is allowed after ambiguous GPU

### Chromium popup corruption: surface lifetime correction

The remaining 320x130 Restore pages popup corruption was reproduced with normal
GPU rendering and sandboxing. Bounded captures showed correct source pixels,
correct uploaded texture, correct producer pbuffer, correct imported texture,
correct compositor output, and correct shared backing pixels. The kernel's
surface list subsequently contained only the main browser window. The trace
showed Core Animation rebinding the same GL context from the popup to that window.

The driver owned surface backing through the GL context and freed the previous
surface on rebind. WindowServer still needed that image. Backing now belongs to
a process-local registry keyed by surface ID, survives detach, context changes
and context destruction, and is reclaimed after WindowServer removes the surface.
Resizing replaces that surface's allocation; local imported resources retain old
allocations through their final GPU use. Failed registry queries are distinguished
from an empty registry, and the Darwin snapshot uses stack storage to avoid
cross-thread overwrites. Same-surface rebinds preserve their backing as well.

Also corrected noncurrent OSMesa synchronization: pending GLThread work is submitted
and then drained before the caller changes the context or drawable. This alone
had not fixed the popup and is not the evidence for the surface lifetime diagnosis.

## Standalone OpenGL 4.6 compute demo

Built `~/Desktop/Radeon GL46 Demo.app` as a PPC64 Cocoa application with its own
Mesa library. The native probe and running demo report AMD TURKS, OpenGL 4.6 Core,
and GLSL 4.60 without version overrides. The system GLD was not replaced for this
experiment. Source: `tools/guest/gl46demo.m`.

The demo combines a GLSL 4.60 ray-marched scene with 8,192 simulated particles.
Compute shaders update persistent particle position/velocity SSBOs and accumulate
particle glow into a second SSBO using GPU atomic adds. A fragment shader reads
that result after shader-storage memory barriers. CPU code supplies time and
presents completed pixel readbacks through Cocoa; simulation and scene rendering
execute on the Radeon GPU. This is not an all-GPU window-presentation path.

Vertex-stage SSBOs are unsupported by this r600 backend (reported limit zero).
An initial compute-to-vertex-buffer version exposed a big-endian storage/fetch
mismatch: raw GPU float storage read as host-endian values was incorrect. The
final demo keeps particle data within compute/fragment SSBO access instead;
it does not apply a driver fix for that outstanding interoperability issue.
The supported BGRA OSMesa framebuffer is converted from ARGB bytes for Cocoa.

Verified hundreds of consecutive frames with GL_NO_ERROR and visible dense
particle output. Capture: `F:/radeonni-leopard-build/gl46-compute-final.png`.
Runtime log: `~/RadeonNI-diagnostics/gl46demo.log`. This does not establish Aurora
or Portal stability, complete 4.6 conformance, or system-framework 4.6 support.

Build used the existing `librdngl.dylib` Ninja target, relinked with an export list
containing only OSMesaCreateContextAttribs, OSMesaMakeCurrent, OSMesaGetProcAddress,
and OSMesaDestroyContext to avoid exporting the bundled C++ runtime. Host build
recipe: `F:/radeonni-leopard-build/link-gl46.sh`, exports: `gl46.exports`.
Native app compilation uses Apple gcc-4.2, `-arch ppc64 -std=gnu99 -O2 -framework Cocoa`.

true. DTrace of WindowServer's `CGXUpdateMagicMenuBar` showed blue wallpaper

The production candidate exposes a host-bridge copy limit to r600. The Darwin
backend detects the `u4-pcie` ancestor; r600 then bounds and synchronizes only

ordering mechanism has not been established, and larger MRRS must not be
advertised as a successful fix.

### Confirmed upstream gaps

- Runtime GPU recovery and reset-generation reporting: the winsys reset-status
  callback always returns `PIPE_NO_RESET`. Boot-time reset helpers exist; there
  is no complete runtime recovery path to invalidate contexts and resume work.
- Interrupt-driven fences and fault collection: this port polls registers and
  does not implement upstream's interrupt-handler ring and fault reporting.
- ASIC coverage: engine configuration and Mesa family identification are fixed
  to Turks. This is not a validated generic Evergreen/Northern Islands driver.
- Golden register tables: upstream has per-ASIC masked register sequences,
  including Turks, that are absent here. Firmware may set some of the same
  registers; their live values need comparison before porting those writes.
- The upstream PCIe read-request fix needs host constraints; copying its 512-byte
  setting directly fails the G5 byte-verification test.

it does not exclude the producer application's thread. The backing-surface import
loop has the same unsynchronized producer-flush pattern.

both import paths. Prefer submission by the producer with a published fence;
any consumer-triggered producer flush needs serialization with producer rendering
and context destruction, with defined lock ordering. A null check in the winsys
would hide the race and lose buffer lifetime tracking.
